Three Azure SQL options and how to choose between them

Infrastructure as a Service

SQL Server on Azure VM

SQL Server with operating-system access and control over the engine version. You manage SQL configuration, patching and availability, with Azure automation available.

Platform as a Service · instance scope

SQL Managed Instance

A managed instance with broad SQL Server compatibility. Microsoft manages the OS, engine patching, backups and built-in availability; some instance features have restrictions.

Platform as a Service · database scope

Azure SQL Database

Managed databases, individually or in elastic pools. A good candidate when the application can work within database-scoped capabilities rather than requiring an unchanged SQL instance.

Compute choices: provisioned for allocated capacity, or serverless for automatically scaling single databases with per-second billing and CPU/memory minimums. Eligible General Purpose serverless databases can auto-pause; Hyperscale serverless cannot.

Choose deployment fit first, then compute. Managed Instance is a deployment option; serverless is a compute tier of Azure SQL Database, not a mode of MI. They can still be alternative destinations when a workload fits both. See Microsoft's official decision tree.

Three questions decide it

Use these to shortlist a destination, not certify compatibility. Confirm exact feature support, database size, performance and HA/DR requirements before choosing a configuration.

1

Does the workload need the operating system?

Choose a VM when dependencies on the SQL host must remain unchanged. If you can move those dependencies to other services, PaaS may still fit.
  • Host access or local execution — RDP, an installed backup/monitoring agent, a local executable, xp_cmdshell or sp_OACreate that the application must continue to use on the SQL host.
  • Local or UNC files — FILESTREAM, FileTable, or an unchanged BULK INSERT / backup workflow against a file share. Azure Storage-based import and backup alternatives may remove the host dependency.
  • A specific engine version or unsupported configuration — vendor certification pins an engine version, or the workload requires host configuration unavailable in PaaS. An old source version alone is not a VM requirement: SQL Server 2008/2012/2014 compatibility levels are 100/110/120, respectively.
  • A third-party linked-server provider — an Oracle OPENQUERY dependency that must stay unchanged needs a VM or redesign; MI does not support arbitrary third-party RDBMS providers.
Must keep these unchanged → Consider SQL Server on Azure VM
No, or willing to redesign them → keep going.
These are not automatic VM requirements

MI supports Resource Governor, managed DTC and the sysadmin SQL role within its managed-service boundaries. SQL administration is not OS access.

MI can host supported SSRS catalog databases; the report-server application runs separately. External tables have supported scenarios in MI and SQL Database (some SQL Database capabilities are in preview): check the connector, not just the PolyBase label.

MI Machine Learning Services support depends on update policy: Python/R is available only under the SQL Server 2022 update policy, not SQL Server 2025 or Always-up-to-date. Check lifecycle restrictions before relying on it.

2

Does it need instance-level SQL features?

MI is a strong candidate for supported instance dependencies that you do not want to rewrite. Near-full compatibility does not mean every feature behaves identically.
  • SQL Server Agent jobs — supported T-SQL, replication and SSIS job steps. MI does not support Agent alerts, proxies or command-shell steps. SQL Database Elastic Jobs is an alternative for suitable workloads, not a drop-in replacement.
  • Native cross-database queries — SELECT … FROM OtherDb.dbo.Table, three-part names and cross-database synonyms. SQL Database alternatives can require redesign.
  • Supported linked servers — SQL-family targets using supported providers and authentication. Validate the specific endpoint; an Oracle linked server is not covered.
  • Service Broker or CLR — user queues/services and CREATE ASSEMBLY. Validate networking, assembly restrictions and any external activation process separately.
  • Transactional replication publishing/distribution — MI supports documented topologies. Check participants and restrictions rather than assuming all replication modes fit.
  • Instance-wide semantics or portability — an application requires cross-database global-temp sharing or a supported route back to SQL Server. Verify exact security, version and reverse-migration requirements.
Needs supported instance features → Consider Azure SQL Managed Instance
No, or willing to rework them → evaluate Azure SQL Database, then question 3.
Features that do not require MI by themselves

CDC is supported in SQL Database vCore tiers and DTU S3 or above. SQL Database also supports SQL logins mapped to users in multiple databases and ##GlobalTemp shared across sessions within the same database. These are not automatic MI gates.

SSISDB can be hosted by SQL Database or MI. In the Azure-SSIS managed execution path, packages run on separately provisioned Azure-SSIS Integration Runtime, not inside the database service. MI adds Agent scheduling integration.

Log Replay Service provides log-based migration to MI; it is not traditional ongoing log-shipping HA/DR. Map recovery requirements to supported target capabilities.

3

Is the load steady, or does it come and go?

Once SQL Database meets the application's requirements, choose its compute model. Activity patterns and latency tolerance matter as much as database size.
  • Steady use or predictable response times — an always-on order-processing service, sustained reporting or a job that cannot tolerate resume delays: consider provisioned compute.
  • Intermittent use with idle periods — a departmental app or test database whose clients tolerate resume delays and implement retries: consider serverless.
  • Many databases with varying demand — compare elastic pools as well as individual databases; shared provisioned capacity may be more economical.
  • Price the workload, not connected hours alone — use CPU and memory demand, configured minimums, idle duration, pause eligibility and regional prices. There is no universal one-third-CPU, seven-hour or sixteen-hour break-even.
Steady / latency-sensitive → Consider provisioned SQL Database
Intermittent / resume-tolerant → Consider SQL Database serverless
Serverless billing and availability details

While online, billable compute each second is based on the greatest of CPU consumed, memory normalized to vCores, and configured CPU/memory minimums. Storage is charged even while paused. Remaining online does not turn serverless into provisioned billing.

Auto-pause is General Purpose only, when enabled and eligible. It requires zero sessions and zero user CPU throughout the configured delay. Polling connections and features such as geo-replication/failover groups or long-term retention can prevent it. Hyperscale serverless autoscales but does not auto-pause.

AHB does not apply to serverless. Eligible provisioned vCore configurations can benefit, but DTU and new Hyperscale databases are excluded. Verify current eligibility and any transitional rights when comparing prices.

Existing availability groups do not automatically rule out serverless or require Business Critical. Map RTO/RPO, zone redundancy and read-scale needs to the target. Memory-optimized tables are not supported in General Purpose/Hyperscale serverless; Hyperscale does support some other In-Memory OLTP object types.
