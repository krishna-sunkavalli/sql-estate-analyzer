Azure SQL options and how to choose between them

Infrastructure as a Service

SQL Server on Azure VM

The SQL Server you run today, on someone else's hardware. You keep the operating system — and you keep patching it.

Platform as a Service · instance scope

SQL Managed Instance

Near-full SQL Server compatibility with no OS to run. Keeps the instance-level features applications quietly depend on.

Platform as a Service · database scope

Azure SQL Database

A single database as a service. Lowest administration, but nothing outside that one database comes with it.

A compute tier of Azure SQL Database

Serverless

Not a separate product. Azure SQL Database billed per second on the compute actually used, pausing when idle.

The most common misunderstanding: Managed Instance and serverless are not alternatives to each other. Managed Instance is an instance; serverless is a billing and scaling mode for a single database. You choose instance-versus-database first, and only then — if you landed on a single database — provisioned versus serverless.

Three questions decide it

1

Does the workload need the operating system?

Anything that reaches outside the database engine and onto the machine.
  • Console or RDP access to the server
  • Third-party agents — backup, monitoring, antivirus
  • Full sysadmin, or control over instance configuration
  • Files on disk: FILESTREAM, FileTable, BULK INSERT from a local path
  • Features Azure SQL PaaS does not offer at all, such as SSRS or PolyBase
Yes → SQL Server on Azure VM
No → keep going.
2

Does it need instance-level SQL features?

Things that live on the instance rather than inside one database — the usual reason a lift to Azure SQL Database fails late.
  • SQL Server Agent jobs
  • Queries that cross databases, or linked servers
  • Service Broker, CLR assemblies
  • Instance-level logins shared across databases
  • SSIS packages, or a replication distributor
Yes → Azure SQL Managed Instance
No → keep going.
3

Is the load steady, or does it come and go?

You are on Azure SQL Database either way. This only picks how it is sized and billed.
  • Steady and predictable — always-on line-of-business, reporting under constant use
  • Intermittent or idle — dev and test, seasonal work, internal tools used a few hours a day
Steady → Azure SQL Database, provisioned
Intermittent → Azure SQL Database, serverless
Serverless costs more per vCore-hour than provisioned but bills only while the database is awake, so it wins below roughly two-thirds utilisation and loses above it. It is General Purpose and Hyperscale only — never Business Critical — so anything needing In-Memory OLTP or an availability group rules it out.

Least effort is not least cost, and the two often point in opposite directions. An estate running Enterprise edition can be cheaper on a VM than on Managed Instance, because Enterprise features push Managed Instance to the Business Critical tier at roughly twice the General Purpose rate.
