Azure SQL options and how to choose between them

Infrastructure as a Service

SQL Server on Azure VM

The SQL Server you run today, on someone else's hardware. You keep the operating system — and you keep patching it.

Platform as a Service · instance scope

SQL Managed Instance

Near-full SQL Server compatibility with no OS to run. Keeps the instance-level features applications quietly depend on.

Platform as a Service · database scope

Azure SQL Database

A single database as a service. Lowest administration, but nothing outside that one database comes with it.

A compute tier of Azure SQL Database

Serverless

Not a separate product. Azure SQL Database billed per second on the compute actually used, pausing when idle.

The most common misunderstanding: Managed Instance and serverless are not alternatives to each other. Managed Instance is an instance; serverless is a billing and scaling mode for a single database. You choose instance-versus-database first, and only then — if you landed on a single database — provisioned versus serverless.

Three questions decide it

1

Does the workload need the operating system?

Anything that reaches outside the database engine and onto the machine. None of it survives a move to PaaS.
  • Files on disk — FILESTREAM, FileTable, BULK INSERT or OPENROWSET from a UNC path, xp_cmdshell, sp_OACreate
  • Backups to a share — BACKUP DATABASE … TO DISK = '\\nas\sql\...', or a third-party backup agent such as Veeam, Commvault or Rubrik
  • Agents on the box — monitoring (SCOM, Datadog, SolarWinds), antivirus exclusions, or a scheduler that runs .exe and PowerShell steps
  • Instance configuration — trace flags, sp_configure beyond what PaaS exposes, custom tempdb file layout, Resource Governor, soft-NUMA, Lock Pages in Memory
  • Not offered in PaaS at all — SSRS report server databases, SSAS, PolyBase and external tables, Machine Learning Services (sp_execute_external_script), Distributed Transaction Coordinator, FileTable-backed applications
  • Versions older than 2016 that you do not intend to upgrade — Azure SQL PaaS needs compatibility level 100 or above
Yes → SQL Server on Azure VM
No → keep going.
2

Does it need instance-level SQL features?

Things that live on the instance rather than inside one database. This is the usual reason a lift to Azure SQL Database fails late, because the code compiles fine and only breaks at run time.
  • SQL Server Agent — scheduled jobs, alerts, operators, Database Mail. Azure SQL Database has Elastic Jobs, but that is a rewrite, not a migration
  • Cross-database access — SELECT … FROM OtherDb.dbo.Table, three-part names, synonyms pointing at another database, a shared lookup or staging database
  • Linked servers — OPENQUERY, four-part names, distributed queries to another SQL Server or Oracle
  • Service Broker — user queues, services and contracts, external activation
  • CLR — CREATE ASSEMBLY, .NET stored procedures or aggregates
  • Instance-level security — SQL logins shared across databases, server roles, credentials and proxies, server-scoped audits, cross-database ownership chaining
  • SSIS — an SSISDB catalog, or packages that run under the Agent
  • Transactional replication as a publisher or distributor, change data capture, log shipping
  • Global temp tables and tempdb tricks — ##GlobalTemp shared across sessions
Yes → Azure SQL Managed Instance
No → keep going.
3

Is the load steady, or does it come and go?

You are on Azure SQL Database either way. This only picks how it is sized and billed — and unlike the first two questions, the answer is in your own telemetry rather than your schema.
  • Steady and predictable — an always-on line-of-business database, a reporting database queried through the working day, anything with a nightly ETL window that must not wait for a cold start
  • Intermittent or idle — development and test copies, a departmental app used a few hours a day, seasonal or month-end workloads, a database behind an internal tool nobody touches overnight
  • Where to look — average CPU against peak in Query Store or perfmon. A database averaging under a third of its cores, with long flat stretches rather than a steady hum, is the serverless case
  • The quick test — count the hours a day something is actually connected. Without Hybrid Benefit, serverless is cheaper below roughly sixteen hours. With Hybrid Benefit that falls to about seven, because the benefit cuts the provisioned rate and does not apply to serverless at all
Steady → Azure SQL Database, provisioned
Intermittent → Azure SQL Database, serverless
Serverless costs more per vCore-hour than provisioned but bills only while the database is awake. It is General Purpose and Hyperscale only — never Business Critical — so anything needing In-Memory OLTP or an availability group rules it out.

Two things catch people out. Azure Hybrid Benefit does not apply to serverless, so an estate with Software Assurance sees the provisioned rate fall while serverless stays where it is — which moves the break-even a long way in favour of provisioned. And a database only auto-pauses when nothing is connected: a monitoring tool or an application connection pool that polls every minute will keep it awake, and you will pay as though it were provisioned while getting none of the cost benefit.

Least effort is not least cost, and the two often point in opposite directions. An estate running Enterprise edition can be cheaper on a VM than on Managed Instance, because Enterprise features push Managed Instance to the Business Critical tier at roughly twice the General Purpose rate.
